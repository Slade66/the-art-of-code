- **`uniqueIndex` 与 `not null`**
  collapsed:: true
	- **`uniqueIndex`（唯一索引）的作用：**
		- **核心作用**：确保一列（或多列组合）中的所有值都是唯一的，不能重复。
		- **如何工作**：当你插入（`INSERT`）或更新（`UPDATE`）记录时，数据库会检查该列的值是否已存在于索引中。如果已存在，操作将被拒绝，并返回唯一性冲突的错误。
		- **额外好处**：作为索引，它还能显著提高查询（`SELECT`）的速度。当根据此列查找数据时，数据库可以通过索引快速定位记录，而无需扫描整个表（Full Table Scan）。
	- **`not null` （非空约束）的作用：**
		- **核心作用**：确保一列中的每个值都不能为空，必须有一个有效值。
		- **如何工作**：当插入或更新记录时，如果该列未赋值或显式赋值为 `NULL`，数据库会拒绝操作，并返回错误，提示该列不能为空。
	- **`uniqueIndex` + `not null`**
		- `uniqueIndex` 只确保所有 **“有值的”** 记录是唯一的，而 `not null` 确保 **“所有记录都有值”**。
		- 将这两个约束结合在一起，形成了一个完美的逻辑闭环：
			- `not null` 约束首先确保每一行记录的该列都必须有一个确切的值，从根本上避免了 `NULL` 的出现。
			- 在此基础上，`uniqueIndex` 约束进一步确保这些 **“存在的、非空的值”** 是唯一的。
		- **最终结果**：该列中的每个值都必须存在（`not null`），且必须是唯一的（`uniqueIndex`）。这实现了我们期望的“真正的”唯一性，没有任何例外或特殊情况。
- **数据库如何看待 `NULL`**
  collapsed:: true
	- 在 SQL 标准中，`NULL` 是一个特殊的值，既不代表 `0`，也不代表空字符串 `''`，更不代表任何具体的值。**`NULL` 代表的是“未知”、“缺失”或“不适用”**。
	- 基于这一哲学，`NULL` 与任何值进行比较的结果都是“未知（`unknown`）”，而不是 `true` 或 `false`，包括 `NULL` 与另一个 `NULL` 的比较。
	- 考虑这个逻辑问题：“一个未知的值” 是否等于 “另一个未知的值”？
	- 答案是：**不确定**。由于我们无法知道它们分别代表什么，因此不能判断它们是否相等。
	- 因此，在 SQL 中，`NULL = NULL` 的结果不是 `true`，而是 `unknown`（在实际操作中，`WHERE` 子句会将其视为 `false`）。
- **`uniqueIndex` 如何看待 `NULL`**
  collapsed:: true
	- 当 `uniqueIndex` 检查新插入的 `NULL` 值是否“重复”时，它会查看索引中是否已有 `NULL` 值。根据 `NULL != NULL` 的原则，数据库认为新插入的 `NULL` 与任何已存在的 `NULL` 都不相等。

- **MySQL 如何实现枚举？**
	- **使用内置的 ENUM 类型**
	  collapsed:: true
		- `ENUM` 类型的取值只能在表创建时定义的一组值中选择。
		- **示例：**
			- ```sql
			  CREATE TABLE users (
			      id INT PRIMARY KEY AUTO_INCREMENT,
			      username VARCHAR(50),
			      status ENUM('active', 'inactive', 'pending', 'banned') DEFAULT 'pending'
			  );
			  ```
		- **优点：**
			- **存储效率高：**MySQL 在内部将 `ENUM` 值存储为整数（1, 2, 3...），非常节省空间。
			- **可读性好：**查询时直接显示字符串，而不是晦涩的数字。
			- **数据验证：**这种方式直接在数据库层面限制字段只能存储预定义的字符串，数据库会自动拒绝不在列表中的非法字符串。
		- **缺点：**
			- **修改困难：**如果想增加一个新的状态，需要执行 `ALTER TABLE`，在大型表上这可能会导致锁表，影响性能。
			- **非标准：**`ENUM` 是 MySQL 的特有特性，迁移到 PostgreSQL 或 Oracle 时可能不兼容。
	- **使用字典表（状态表）并通过外键关联**
	  collapsed:: true
		- **示例：**
			- ```sql
			  # 创建枚举表
			  CREATE TABLE user_statuses (
			      id TINYINT PRIMARY KEY,
			      status_name VARCHAR(20) NOT NULL UNIQUE
			  );
			  
			  # 在主表中引用
			  CREATE TABLE users (
			      id INT PRIMARY KEY AUTO_INCREMENT,
			      status_id TINYINT,
			      FOREIGN KEY (status_id) REFERENCES user_statuses(id)
			  );
			  ```
		- **优点：**
			- **扩展性强：**增加新状态只需 `INSERT` 一行数据，无需修改表结构。
			- **支持更多信息：**枚举表可以存储描述、排序权重等额外字段。
			- **跨数据库通用：**这是 SQL 的标准做法。
	- **使用 VARCHAR + CHECK 约束（MySQL 8.0.16+）**
	  collapsed:: true
		- 如果你不想使用 `ENUM` 也不想建新表，可以使用 `CHECK` 约束来限制 `VARCHAR` 的取值。
		- **示例：**
			- ```sql
			  CREATE TABLE orders (
			      id INT PRIMARY KEY,
			      priority VARCHAR(10),
			      CONSTRAINT check_priority CHECK (priority IN ('Low', 'Medium', 'High'))
			  );
			  ```
		- **优点：**
			- **通用性好：**标准 SQL，几乎所有主流数据库都支持。
			- **支持复杂的校验逻辑：**
				- 简单的状态检查：`CHECK (status IN ('draft', 'published'))`
				- 复合逻辑：`CHECK (price > 0 AND discount <= price)`
		- **缺点：**
			- **修改约束需要改表：**
				- 修改 `CHECK` 约束也需要执行 `ALTER TABLE` 语句，但它的代价通常比 `ENUM` 小得多。
				- **修改  ENUM  的代价：**
					- 如果你想给 `ENUM('A', 'B')` 增加一个 `'C'`，MySQL 在某些情况下可能需要重建整个表。对于千万级的大表，这会导致长时间锁表。
				- **修改 CHECK 的代价：**
					- **删除旧约束：**`ALTER TABLE 表名 DROP CHECK 约束名;`
					  logseq.order-list-type:: number
					- **添加新约束：**`ALTER TABLE 表名 ADD CONSTRAINT 约束名 CHECK (字段 IN ('A', 'B', 'C'));`
					  logseq.order-list-type:: number
					- **注意：**虽然添加 `CHECK` 约束本身很快，但 MySQL 会扫描全表以确保现有数据符合新规则。如果表非常大，这个扫描过程依然会消耗 I/O。
	- **怎么选？**
	  collapsed:: true
		- **选 ENUM：**
			- 当你追求极致性能且数据几乎不变。
			- 数据量巨大（亿级），对存储空间极其敏感。
			- 成员非常固定（如：性别、周一到周日），不会改动。
		- **选 CHECK：**
			- 当你需要跨数据库兼容或复杂逻辑（限制条件不仅仅是 “几个字符串”）。
		- **选 “字典表”：**
			- 绝大多数业务逻辑的首选。
			- 如果枚举项经常发生变动，就不适合使用上述任何一种方式。应当直接建立一张状态表，并通过外键进行关联。这样新增状态只需插入一条 `INSERT` 语句，无需修改表结构，对现有业务也不会产生影响（不会锁表）。
